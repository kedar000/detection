AI Overlay Detection — Behavioral Data Collection
======================================================

1. Problem
----------

The goal is to collect browser-side behavioral signals during an online test and
send them from the frontend to the backend for later normalization and model-based
analysis.

For the initial implementation, the focus is on written-answer questions only.

The frontend should capture observable user behavior as a chronological event
stream. The frontend should not make cheating decisions or perform complex
behavioral analysis. It should collect the raw observations required by the
backend.

2. Final Approach
-----------------

The current approach is:

Frontend
    ↓
Raw behavioral events
    ↓
Backend
    ↓
Normalization / feature extraction
    ↓
Behavioral / temporal representation
    ↓
AI model or rule-based analysis

The frontend will send raw events together with the current answer length and
cumulative blur count.

The backend normalization layer will calculate derived behavioral features from
the ordered event stream.

This keeps the frontend simple and preserves the original event sequence so that
new features can be derived later without changing the data collection format.

3. Scope — Initial Version
--------------------------

For now, the system will support written-answer questions.

The initial behavioral signals are:

- Focus / blur
- Page visibility
- Keyboard events
- Paste events
- Answer changes
- Question timing

Selection / multiple-choice questions are intentionally out of scope for this
version.

Later, the same behavioral framework can be extended with selection-specific
events and features.

4. Frontend → Backend Contract
------------------------------

Each event sent from the frontend follows this structure:

{
  "session_id": "session_001",
  "question_id": "q_01",
  "timestamp": 1724580000000,
  "answer_length": 5,
  "blur_count": 1,
  "event": {
    "type": "keydown",
    "key": "K"
  }
}

Fields:

session_id
----------
Identifies the current test session.

question_id
-----------
Identifies the question associated with the event.

timestamp
---------
The timestamp at which the event occurred.

answer_length
-------------
The current length of the answer at the time of the event.

The frontend does not calculate answer changes. It only reports the current
answer length.

blur_count
----------
The cumulative number of focus losses at the time of the event.

The frontend does not need to send a separate blur event. The current blur count
is maintained as state.

event
-----
Contains the observable event generated by the browser.

Examples:

{
  "type": "keydown",
  "key": "K"
}

{
  "type": "keyup",
  "key": "K"
}

{
  "type": "paste"
}

{
  "type": "visibility_change",
  "state": "hidden"
}

{
  "type": "visibility_change",
  "state": "visible"
}

{
  "type": "question_opened"
}

{
  "type": "question_closed"
}

5. Keyboard Event Handling
--------------------------

Keyboard events are sent as individual keydown and keyup events.

For example, Command + \ is represented as:

Meta keydown
\ keydown
\ keyup
Meta keyup

No separate "modifiers" field is required.

The backend can reconstruct keyboard combinations from the ordered keyboard
events and their timestamps.

6. Answer Length and Answer Changes
-----------------------------------

The frontend sends the current answer length with each event.

Example:

Event 1:
answer_length = 10

Event 2:
answer_length = 15

The backend normalization layer calculates:

answer_length_change = 15 - 10
                      = +5

This allows the backend to identify normal typing, deletions, replacements,
and sudden increases in answer size.

For example:

Keyboard activity:
2 keyboard events

Answer:
100 characters → 900 characters

The backend can derive:

answer_length_change = +800

The relationship between keyboard activity and answer growth can then become a
behavioral feature.

This is intentionally calculated in the backend rather than the frontend.

7. Question Timing
------------------

The frontend will provide question lifecycle events:

- question_opened
- keyboard activity
- question_closed

The backend can derive temporal features from the timestamps.

The backend can determine events such as:

- Time from question opened to first typing
- Total question duration
- Active typing duration
- Idle periods
- Time between typing bursts
- Time between blur/focus changes and subsequent activity
- Time between paste events and answer changes

Typing started and typing stopped do not need to be explicitly generated by the
frontend.

They can be derived by the backend from keyboard activity and configurable
inactivity thresholds.

8. Behavioral / Temporal Data Before Normalization
---------------------------------------------------

Before normalization, the backend should receive a chronological stream of
events that preserves:

- Which session the event belongs to
- Which question the event belongs to
- When the event occurred
- Current answer length
- Current blur count
- The raw browser event
- Keyboard key information when applicable
- Visibility state when applicable

Example sequence:

question_opened
    ↓
keydown K
    ↓
keyup K
    ↓
keydown e
    ↓
keyup e
    ↓
keydown Meta
    ↓
keydown \
    ↓
keyup \
    ↓
keyup Meta
    ↓
visibility_change
    ↓
paste
    ↓
keydown ...
    ↓
question_closed

The backend normalization layer will use this chronological sequence to produce
the derived behavioral and temporal features.

9. Responsibility Boundary
--------------------------

Frontend responsibility:

- Capture observable browser events
- Attach session_id and question_id
- Add timestamp
- Maintain current answer_length
- Maintain cumulative blur_count
- Send events in chronological order

Backend responsibility:

- Validate incoming events
- Preserve event ordering
- Calculate answer changes
- Calculate typing and timing features
- Calculate temporal relationships between events
- Normalize the behavioral data
- Prepare the resulting representation for later analysis/model input``

The frontend should not determine whether a candidate is cheating.

10. Future Extension
--------------------

This structure is intentionally designed for the written-answer case first.

Once the written behavioral pipeline is stable, selection/multiple-choice
questions can be added using the same session/question/event structure.

Additional selection-specific events and features can then be introduced without
changing the core behavioral event architecture.
