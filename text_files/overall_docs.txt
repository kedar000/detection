AI Overlay Detection — Behavioral Data Collection
======================================================

1. Problem
----------

The goal is to collect browser-side behavioral signals during an online test and
send them from the frontend to the backend for later normalization and model-based
analysis.

For the initial implementation, the focus is on written-answer questions only.

The frontend should capture observable user behavior as a chronological event
stream. The frontend should not make cheating decisions or perform complex
behavioral analysis. It should collect the raw observations required by the
backend.

2. Final Approach
-----------------

The current approach is:

Frontend
    ↓
Raw behavioral events
    ↓
Backend
    ↓
Normalization / feature extraction
    ↓
Behavioral / temporal representation
    ↓
AI model or rule-based analysis

The frontend will send raw events together with the current answer length and
cumulative blur count.

The backend normalization layer will calculate derived behavioral features from
the ordered event stream.

This keeps the frontend simple and preserves the original event sequence so that
new features can be derived later without changing the data collection format.

3. Scope — Initial Version
--------------------------

For now, the system will support written-answer questions.

The initial behavioral signals are:

- Focus / blur
- Page visibility
- Keyboard events
- Paste events
- Answer changes
- Question timing

Selection / multiple-choice questions are intentionally out of scope for this
version.

Later, the same behavioral framework can be extended with selection-specific
events and features.

4. Frontend → Backend Contract
------------------------------

Each event sent from the frontend follows this structure:

{
  "session_id": "session_001",
  "question_id": "q_01",
  "timestamp": 1724580000000,
  "answer_length": 5,
  "blur_count": 1,
  "event": {
    "type": "keydown",
    "key": "K"
  }
}

Fields:

session_id
----------
Identifies the current test session.

question_id
-----------
Identifies the question associated with the event.

timestamp
---------
The timestamp at which the event occurred.

answer_length
-------------
The current length of the answer at the time of the event.

The frontend does not calculate answer changes. It only reports the current
answer length.

blur_count
----------
The cumulative number of focus losses at the time of the event.

The frontend does not need to send a separate blur event. The current blur count
is maintained as state.

event
-----
Contains the observable event generated by the browser.

Examples:

{
  "type": "keydown",
  "key": "K"
}

{
  "type": "keyup",
  "key": "K"
}

{
  "type": "paste"
}

{
  "type": "visibility_change",
  "state": "hidden"
}

{
  "type": "visibility_change",
  "state": "visible"
}

{
  "type": "question_opened"
}

{
  "type": "question_closed"
}

5. Keyboard Event Handling
--------------------------

Keyboard events are sent as individual keydown and keyup events.

For example, Command + \ is represented as:

Meta keydown
\ keydown
\ keyup
Meta keyup

No separate "modifiers" field is required.

The backend can reconstruct keyboard combinations from the ordered keyboard
events and their timestamps.

6. Answer Length and Answer Changes
-----------------------------------

The frontend sends the current answer length with each event.

Example:

Event 1:
answer_length = 10

Event 2:
answer_length = 15

The backend normalization layer calculates:

answer_length_change = 15 - 10
                      = +5

This allows the backend to identify normal typing, deletions, replacements,
and sudden increases in answer size.

For example:

Keyboard activity:
2 keyboard events

Answer:
100 characters → 900 characters

The backend can derive:

answer_length_change = +800

The relationship between keyboard activity and answer growth can then become a
behavioral feature.

This is intentionally calculated in the backend rather than the frontend.

7. Question Timing
------------------

The frontend will provide question lifecycle events:

- question_opened
- keyboard activity
- question_closed

The backend can derive temporal features from the timestamps.

The backend can determine events such as:

- Time from question opened to first typing
- Total question duration
- Active typing duration
- Idle periods
- Time between typing bursts
- Time between blur/focus changes and subsequent activity
- Time between paste events and answer changes

Typing started and typing stopped do not need to be explicitly generated by the
frontend.

They can be derived by the backend from keyboard activity and configurable
inactivity thresholds.

8. Behavioral / Temporal Data Before Normalization
---------------------------------------------------

Before normalization, the backend should receive a chronological stream of
events that preserves:

- Which session the event belongs to
- Which question the event belongs to
- When the event occurred
- Current answer length
- Current blur count
- The raw browser event
- Keyboard key information when applicable
- Visibility state when applicable

Example sequence:

question_opened
    ↓
keydown K
    ↓
keyup K
    ↓
keydown e
    ↓
keyup e
    ↓
keydown Meta
    ↓
keydown \
    ↓
keyup \
    ↓
keyup Meta
    ↓
visibility_change
    ↓
paste
    ↓
keydown ...
    ↓
question_closed

The backend normalization layer will use this chronological sequence to produce
the derived behavioral and temporal features.

9. Responsibility Boundary
--------------------------

Frontend responsibility:

- Capture observable browser events
- Attach session_id and question_id
- Add timestamp
- Maintain current answer_length
- Maintain cumulative blur_count
- Send events in chronological order

Backend responsibility:

- Validate incoming events
- Preserve event ordering
- Calculate answer changes
- Calculate typing and timing features
- Calculate temporal relationships between events
- Normalize the behavioral data
- Prepare the resulting representation for later analysis/model input``

The frontend should not determine whether a candidate is cheating.

10. Future Extension
--------------------

This structure is intentionally designed for the written-answer case first.

Once the written behavioral pipeline is stable, selection/multiple-choice
questions can be added using the same session/question/event structure.

Additional selection-specific events and features can then be introduced without
changing the core behavioral event architecture.

AI Overlay Detection — Initial ML Model Design
================================================

1. Problem Definition
---------------------

The frontend collects behavioral events generated while a candidate is taking a written test.

The first ML prototype will treat a sequence of behavioral events as one training sample.

Example:

Event 1 → Event 2 → Event 3 → ... → Event N

The model will analyze the complete sequence and generate a risk score representing how suspicious the observed behavior is.

For the first version, mouse-movement events are excluded.


2. Why a Sequence Model
-----------------------

The order and timing of behavioral events are important.

The model should not evaluate events independently. The same event can have different meanings depending on what happened before and after it.

For example:

Normal:

KEY_DOWN → KEY_UP → KEY_DOWN → KEY_UP

Potentially more suspicious pattern:

KEY_DOWN → KEY_UP → BLUR → FOCUS → COMMAND_DOWN → "/"_DOWN → "/"_UP → COMMAND_UP

The goal is therefore to learn behavioral patterns across a sequence rather than only aggregate counts.

A sequence model can learn:

- Event order
- Repeated event patterns
- Event combinations
- Temporal relationships
- Changes in behavior over a sequence
- Context surrounding potentially suspicious events

This matches the intended input to the system:

Frontend event stream → ordered sequence → ML model → risk score.


3. Why GRU
----------

The first sequence model selected for the prototype is GRU (Gated Recurrent Unit).

GRU is appropriate because it is designed to process sequential data while maintaining information about previous events.

Reasons for selecting GRU for the first prototype:

1. It directly supports sequential event data.
2. It can learn dependencies between earlier and later events.
3. It is simpler and lighter than a Transformer.
4. It generally requires less data and computational complexity than a large Transformer.
5. It is easier to prototype and debug.
6. It provides a strong starting point for later comparison with LSTM or Transformer models.

The project is starting with a dataset that must be created from scratch. Therefore, a simpler sequence model is preferred initially instead of starting with a Transformer.

LSTM remains a possible comparison model later. Transformer can be evaluated after sufficient real training data is available.

XGBoost/Random Forest may also be used as non-sequential baselines, but they are not the primary model because the main requirement is to learn from event order and sequence.


4. Initial Model Pipeline
-------------------------

The initial architecture is:

Event Encoding
      ↓
Event Embedding
      ↓
GRU
      ↓
Dense Layer
      ↓
Sigmoid
      ↓
Risk Score


4.1 Event Encoding
------------------

Frontend events are converted into a machine-readable representation.

The neural network cannot directly process event names such as:

KEY_DOWN
KEY_UP
BLUR
FOCUS
ANSWER_LENGTH_ANOMALY

Therefore, event types will be encoded into IDs or another numerical representation.

Example:

KEY_DOWN               → 1
KEY_UP                 → 2
BLUR                   → 3
FOCUS                  → 4
ANSWER_LENGTH_ANOMALY  → 5

The exact encoding scheme will be finalized during dataset design.


4.2 Event Embedding
-------------------

Encoded event IDs are converted into learned vector representations.

Example conceptually:

KEY_DOWN → [vector]
KEY_UP   → [vector]
BLUR     → [vector]
FOCUS    → [vector]

The embedding allows the model to learn relationships between different event types.

The embedding layer is provided by the ML framework and does not need to be implemented manually.


4.3 GRU
-------

The event embeddings are passed to the GRU in chronological order.

Conceptually:

Event 1 → GRU → hidden state 1
Event 2 → GRU → hidden state 2
Event 3 → GRU → hidden state 3
...
Event N → GRU → final hidden state

The GRU maintains internal state while processing the sequence. Its gates and internal mathematical operations are handled by the ML framework.

The final GRU representation is used to classify the overall sequence.


4.4 Dense Layer
---------------

The final GRU representation is passed to a Dense (fully connected) layer.

The Dense layer converts the learned sequence representation into a value that can be used for classification.


4.5 Sigmoid
-----------

A sigmoid activation converts the final model output into a value between 0 and 1.

Example:

0.05 → low risk
0.30 → relatively low risk
0.60 → elevated risk
0.85 → high risk

This value will be treated as the model's risk score.

Important: the score is not inherently proof of cheating. It represents the model's learned assessment of suspicious behavior and must be calibrated and evaluated using validation data.


5. Final Output
---------------

The initial model output will be:

risk_score ∈ [0, 1]

Example:

{
    "risk_score": 0.82
}

The threshold for actions such as warning, review, or escalation will be decided separately after model evaluation.

The ML model itself should not directly label a candidate as "cheating" based only on the raw score.


6. Event Structure
------------------

The model will receive behavioral events generated by the frontend.

The events are ordered chronologically.

The first version focuses on:

- Keyboard key down
- Keyboard key up
- Answer-length anomaly
- Focus
- Blur
- Other finalized behavioral events as they are added

Mouse movement is excluded from the first version.

The conceptual event sequence can look like:

KEY_DOWN(k)
KEY_UP(k)
KEY_UP(e)
KEY_DOWN(e)
ANSWER_LENGTH_ANOMALY
KEY_UP(r)
BLUR
KEY_DOWN(r)
KEY_DOWN(COMMAND)
KEY_DOWN("/")
KEY_UP("/")
KEY_UP(COMMAND)
...


7. Answer-Length Anomaly Event
------------------------------

Answer length will NOT be sent to the model after every keystroke.

The frontend will derive an anomaly event when the observed answer-length change is disproportionately large compared with the number of relevant keystrokes.

Example:

2 keystrokes
Answer length changes from 10 to 110
Change = +100

This can generate:

ANSWER_LENGTH_ANOMALY

The event can carry numerical information such as the answer-length delta and the number of relevant keystrokes.

Example conceptual structure:

{
    "type": "ANSWER_LENGTH_ANOMALY",
    "length_delta": 100,
    "keystroke_count": 2
}

The exact threshold and fields will be finalized during event-schema and dataset design.

The purpose is to avoid sending normal answer-length changes for every individual keystroke and instead send a higher-level behavioral signal when a disproportionate change is detected.


8. Potentially Suspicious Keystrokes
------------------------------------

Certain keys such as Command, Control, and Option can be assigned an initial suspicion/prior value.

These keys are not inherently cheating events.

Instead, they are considered potentially relevant behavioral signals.

Example conceptual values:

COMMAND → prior suspicion value
CONTROL → prior suspicion value
OPTION  → prior suspicion value

A normal typing key may have:

A → prior suspicion value = 0

The prior value is NOT the final risk score and does not mean that pressing the key is cheating.

The purpose is to give the model additional information that certain events may be more behaviorally relevant.

The model should ultimately learn the importance of these events from training data and their surrounding context.

For example:

COMMAND

may be relatively insignificant by itself, while:

COMMAND_DOWN
"/"_DOWN
"/"_UP
COMMAND_UP
BLUR
FOCUS
ANSWER_LENGTH_ANOMALY

may form a stronger sequence-level signal.


9. Training Sample Definition
-----------------------------

One training sample is a sequence of frontend-generated behavioral events.

Conceptually:

Sample 1:
[
    EVENT_1,
    EVENT_2,
    EVENT_3,
    ...
    EVENT_N
]
→ label

Sample 2:
[
    EVENT_1,
    EVENT_2,
    EVENT_3,
    ...
    EVENT_N
]
→ label

The label will indicate the training target, such as normal or suspicious behavior.

The exact labeling strategy will be defined when the dataset-generation process is designed.


10. Runtime Flow
----------------

During a test:

Frontend
   ↓
Behavioral events
   ↓
Event preprocessing
   ↓
Event sequence/window
   ↓
Event encoding
   ↓
Event embedding
   ↓
GRU
   ↓
Dense
   ↓
Sigmoid
   ↓
Risk score


Example:

100 behavioral events
        ↓
      GRU
        ↓
Risk Score = 0.78


11. Important Design Principle
------------------------------

The model should learn from the sequence, not from a manually written rule saying that one particular event equals cheating.

Individual events can be given prior behavioral relevance, but the final score should be learned from combinations and sequences of events.

The intended progression is:

Individual events
      ↓
Event combinations
      ↓
Temporal patterns
      ↓
Sequence representation
      ↓
Risk score

→ Event Embedding
→ GRU

→ Sigmoid

Output:
